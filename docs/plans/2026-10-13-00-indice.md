# Salas de Chat Seguras — Plan de implementación (índice, rev. 4)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Construir la aplicación de salas de chat seguras del proyecto integrador con microservicios (gateway + auth, rooms, chat, media, stego, audit), con cuentas y RBAC, e implementar, con un test por riesgo, los 16 controles de seguridad (R1–R15 de la Tarea 2 + R16). El primer parcial entrega un corte definitivo: fundaciones, audit, auth, stego y el gateway.

**Architecture:** Nginx es el único punto de entrada: termina TLS 1.3 y en cada request hace un `auth_request` a `auth`, que verifica el JWT RS256 **y** la sesión a la que apunta y devuelve los permisos actuales en cabeceras `X-User-*`. Detrás hay seis servicios FastAPI: cinco con su propia BD dentro de un único PostgreSQL y `stego` sin estado. Los servicios se comunican por REST interno con un token por servicio (allowlist por hash). El chat cifra cada conexión con ECDH P-256 + HKDF + AES-256-GCM, con un *hello* firmado con ECDSA. `stego` valida, analiza (estructura, chi², RS) y sanitiza imágenes; `media` aplica la política (ClamAV, cuarentena, cifrado, descargas firmadas).

**Tech Stack:** Python 3.13, FastAPI, SQLAlchemy 2 async + asyncpg, Alembic, argon2-cffi, PyJWT, cryptography, pyotp, Pillow, numpy, scipy, httpx · PostgreSQL 17 · Nginx 1.27 · ClamAV 1.4 · React 19 + Vite + TypeScript · pytest, vitest, Postman · Docker Compose · GitHub Actions.

**Spec:** `docs/specs/2026-10-12-chat-seguro-design.md` (revisión 4). Cada archivo del plan argumenta desde ese spec; quien implemente lee ambos. Los tickets por persona están en `docs/tickets/`.

## Global Constraints

Valen para **todas** las tareas de **todos** los archivos del plan:

- **Versiones:** Python 3.13 (imagen `python:3.13-slim`), PostgreSQL 17, Nginx 1.27, ClamAV 1.4, Node 24 LTS, React 19, TypeScript ≥ 5.7 en modo `strict`.
- **Paquetes:** `services/shared` es la distribución `chat-shared` (se importa como `shared`); `services/<svc>` es la distribución `<svc>-svc` (se importa como `<svc>_svc`). **Ningún `pyproject.toml` declara `chat-shared` como dependencia**: se instala explícitamente, para evitar *dependency confusion* con un paquete homónimo en PyPI.
- **SQL:** SQLAlchemy `text()` con parámetros nombrados (`:param`). Nunca se interpolan datos en el texto SQL. Si un fragmento SQL constante se elige en código, se marca con `# noqa: S608` y un comentario.
- **Token de servicio:** toda ruta HTTP o WebSocket de un servicio exige `X-Service-Token` válido (middleware de `shared.web`), salvo `GET /health`.
  - Rutas públicas: `Depends(require_gateway)`, `Depends(require_user)` o `Depends(require_perm("<permiso>"))`.
  - Rutas `/internal/*`: `Depends(allow("<llamador>", ...))`.
- **Autorización:** por permiso del catálogo (spec §9.1) o por dueño/miembro de la sala, siempre en el servidor y con los permisos que trae `X-User-Perms`. Nunca por el rol del JWT ni por un campo del cuerpo.
- **Cuerpos:** modelos Pydantic con `model_config = ConfigDict(extra="forbid")`: un campo de más → 422.
- **Errores al cliente:** siempre JSON `{"error": "<mensaje genérico en español>"}`. El detalle va solo a auditoría.
- **Cookies:** `__Host-session` (JWT) y `__Host-device`, con `Secure`, `HttpOnly`, `SameSite=Strict` y `Path=/` (`shared.web.set_cookie`).
- **Secretos:** solo desde `/run/secrets` (`shared.secrets`). Nunca en el código, en variables de entorno ni en `.env` versionado.
- **Transporte:** solo TLS 1.3 hacia el cliente. Nunca `ws://` (lo bloquea el hook `.claude/hooks/guard.py`).
- **Límites:** mensaje ≤ 2000 caracteres (sin controles salvo `\n`/`\t`); trama WS ≤ 16384; subida ≤ 5 MB; imagen ≤ 20 MP; Argon2id `m=64 MiB, t=3, p=4` con ≤ 4 cálculos concurrentes por proceso; 2 salas activas por dueño; 10 registros por IP por hora; 10 análisis por minuto por usuario.
- **Idioma:** identificadores en inglés; comentarios, docstrings, mensajes de error y UI en español.
- **Pruebas:**
  - PostgreSQL real (`deploy/docker-compose.test.yml`, `127.0.0.1:5433`).
  - Servicios vecinos simulados con `shared.testing.Recorder`.
  - Cada riesgo tiene al menos un `test_rNN_*`.
- **Calidad (spec §16.5, §22.1):** complejidad ciclomática ≤ 10 por función (`ruff`, regla `C90`) y cobertura de líneas ≥ 80 % por servicio. Si una función o un servicio no cumple, se parte la función o se agregan pruebas; no se sube el umbral ni se silencia la regla.
- **Correlación y registros (spec §13, §14.1):** el gateway genera `X-Request-ID`; los servicios lo reenvían, lo ponen en sus registros JSON (sin query string) y lo mandan a `audit` como `request_id`. Ninguna tarea registra datos sensibles en los registros.
- **Trazabilidad:** toda tarea que implementa un control actualiza su fila en `docs/trazabilidad-riesgos.md`.
- **Commits:** Conventional Commits en español, **sin líneas de atribución**, en la rama `feat/arquitectura-chat-seguro` (o ramas hijas por persona).
- **Ramas:** prohibido hacer `merge` a `main` hasta que el equipo lo autorice. No se hace `push` ni se abre un PR sin que lo pidan.
- **Archivos en reposo:** todo archivo de `media` se guarda cifrado con AES-256-GCM (DEK por archivo envuelta con `kek_media_v{n}`). El contenido en claro solo existe en memoria.
- **Cumplimiento:** `docs/requisitos.md`, `docs/cumplimiento-normativo.md` y `docs/justificacion-criptografica.md` ya existen. Una tarea que cambie un control, un algoritmo o una clave mantiene alineados esos documentos y la trazabilidad.
- **Nombres heredados de `shared.crypto`:** desde la rev. 4, `totp_aad(admin_id)` recibe el `user_id`, `msg_aad(room_id, session_id)` el `user_id` del autor y `sign_url(key, file_id, session_id, exp)` el `user_id` del destinatario. El código de FND-2 no cambia; solo el valor que se pasa.

## Review Focus

Cinco casos que el spec implica, pero que ningún criterio de aceptación nombra explícitamente. Cada uno tiene un test en la tarea dueña:

1. **Usuario con mayúsculas o espacios.** `" ANA "` y `ana` son la misma cuenta en el registro y en el login; registrar `ANA` cuando existe `ana` → 409. → **ATH-2**, `test_usuario_normalizado_en_registro_y_login`.
2. **Rol asignado a mitad de una sesión.** Un permiso común (`stego:analyze`) vale en la siguiente request sin volver a entrar; un permiso de admin no vale hasta entrar con TOTP. → **ATH-4**, `test_r05_rol_asignado_vale_en_la_siguiente_peticion`; **ATH-3**, `test_r04_permiso_de_admin_sin_totp_no_vale`.
3. **Imágenes que no son RGB** (RGBA, paleta, escala de grises, 16 bits). `stego` las analiza y sanitiza sin 500 y conserva la transparencia. → **STG-2**, `test_modos_de_imagen_no_rgb`.
4. **Volver a subir una imagen descargada del chat.** Los bytes ya sanitizados no van a cuarentena (se reconocen por `clean_sha256`). → **MED-3**, `test_reenvio_de_imagen_sanitizada_no_va_a_cuarentena`.
5. **Mensajes largos multibyte.** 2000 emojis o letras con tilde no deben cerrar la conexión (la trama queda en ~10.8 KB < 16 KB); con 2001 caracteres → 4400. → **CHAT-3**, `test_mensaje_largo_multibyte_no_cierra`.

Sin argumentos, la fábrica lee todo de `/run/secrets` y del entorno; así la arranca `uvicorn --factory`.

**Lint local:** `ruff format services/<svc> && ruff check --fix services/<svc>` (ordena imports y quita los que sobran). La CI usa `ruff check` y `ruff format --check`, sin `--fix`.

## Preparación del entorno local (una vez por integrante)

```bash
py -3.13 -m venv .venv
```
(En macOS/Linux: `python3.13 -m venv .venv`.) Actívalo (`.venv\Scripts\Activate.ps1` en PowerShell, `source .venv/bin/activate` en bash) e instala:
```bash
pip install -e "services/shared[dev]"
```
A medida que se creen los servicios, se instalan con `pip install -e services/<svc>`. Para la BD de pruebas:
```bash
docker compose -f deploy/docker-compose.test.yml up -d
```
