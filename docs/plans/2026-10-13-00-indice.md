# Primer parcial — Plan de implementación (índice)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Entregar lo que el docente pidió en la clase del 22/10/2026: dos microservicios sin interfaz gráfica, probados con Postman y detrás de un API Gateway.
- `auth`: usuarios, roles y permisos (RBAC); el login devuelve un JWT.
- `stego`: API de esteganografía que responde `invalida`, `limpia`, `problema` o `revision_manual`, a la que se entra con el token de `auth`.

Se acompañan de un informe y una demo en vivo, y cada control de seguridad del parcial lleva su test.

**Architecture:** Postman → Nginx (gateway, TLS 1.3) → `auth` y `stego`. El gateway es el único que habla con los dos microservicios. En cada request hace un `auth_request` a `auth`, que verifica el JWT RS256 **y** la sesión a la que apunta, y devuelve la identidad y los permisos actuales en cabeceras `X-User-*`. `stego` exige el permiso `stego:analyze` con esos datos. `auth` tiene su BD en PostgreSQL; `stego` no guarda nada. Los servicios solo aceptan el token de servicio del gateway (allowlist por hash). Los eventos de seguridad son líneas JSON en la salida de cada contenedor. El servicio `audit` queda fuera de alcance en el parcial.

**Tech Stack:** Python 3.13, FastAPI, SQLAlchemy 2 async + asyncpg, Alembic, argon2-cffi, PyJWT, cryptography, Pillow, numpy, scipy · PostgreSQL 17 · Nginx 1.27 · pytest, Postman · Docker Compose · GitHub Actions.

**Spec:** `docs/specs/2026-10-12-chat-seguro-design.md` (revisión 4). La spec describe el sistema completo (salas, chat, media, auditoría encadenada, TOTP); el primer parcial implementa solo lo que dicen estos planes, y donde difieran, mandan los planes. Los tickets están en `docs/tickets/parcial-1/`.

## Global Constraints

Valen para **todas** las tareas de **todos** los archivos del plan:

- **Versiones:** Python 3.13 (imagen `python:3.13-slim`), PostgreSQL 17, Nginx 1.27.
- **Paquetes:** `services/shared` es la distribución `chat-shared` (se importa como `shared`); `services/<svc>` es la distribución `<svc>-svc` (se importa como `<svc>_svc`). **Ningún `pyproject.toml` declara `chat-shared` como dependencia**: se instala explícitamente, para evitar *dependency confusion* con un paquete homónimo en PyPI.
- **SQL:** SQLAlchemy `text()` con parámetros nombrados (`:param`). Nunca se interpolan datos en el texto SQL.
- **Token de servicio:** toda ruta exige `X-Service-Token` válido (middleware de `shared.web`), salvo `GET /health`. El único llamador es el gateway.
  - Rutas públicas: `Depends(require_gateway)`, `Depends(require_user)` o `Depends(require_perm("<permiso>"))`.
  - `/internal/verify` de auth: `Depends(allow("gateway"))`.
- **Autorización:** por permiso del catálogo (`users:manage`, `roles:manage`, `stego:analyze`), siempre en el servidor y con los permisos que trae `X-User-Perms`. Nunca por el rol del JWT ni por un campo del cuerpo.
- **Cuerpos:** modelos Pydantic con `model_config = ConfigDict(extra="forbid")`: un campo de más → 422.
- **Errores al cliente:** siempre JSON `{"error": "<mensaje genérico en español>"}`. El detalle va solo a los registros.
- **Cookies:** `__Host-session` (JWT) y `__Host-device`, con `Secure`, `HttpOnly`, `SameSite=Strict` y `Path=/` (`shared.web.set_cookie`).
- **Secretos:** solo desde `/run/secrets` (`shared.secrets`). Nunca en el código, en variables de entorno ni en `.env` versionado.
- **Transporte:** solo TLS 1.3 hacia el cliente; http → 301.
- **Límites:** subida ≤ 5 MB; imagen ≤ 20 MP; Argon2id `m=64 MiB, t=3, p=4` con ≤ 4 cálculos concurrentes por proceso; 10 registros por IP por hora; 5 logins fallidos por usuario o IP en 15 min; 10 análisis por minuto por usuario.
- **Idioma:** identificadores en inglés; comentarios, docstrings y mensajes de error en español.
- **Pruebas:**
  - PostgreSQL real (`deploy/docker-compose.test.yml`, `127.0.0.1:5433`).
  - Los eventos de seguridad se comprueban con `testing.events(caplog, "<acción>")`.
  - Cada riesgo tiene al menos un `test_rNN_*`.
- **Calidad (spec §16.5, §22.1):** complejidad ciclomática ≤ 10 por función (`ruff`, regla `C90`) y cobertura de líneas ≥ 80 % por servicio. Si una función o un servicio no cumple, se parte la función o se agregan pruebas; no se sube el umbral ni se silencia la regla.
- **Correlación y registros (spec §13):** el gateway genera `X-Request-ID`; los servicios lo ponen en sus registros JSON (sin query string). Ninguna tarea registra datos sensibles.
- **Trazabilidad:** toda tarea que implementa un control actualiza su fila en `docs/trazabilidad-riesgos.md`.
- **Commits:** Conventional Commits en español, **sin líneas de atribución**, en la rama `feat/arquitectura-chat-seguro` (o ramas hijas por persona).
- **Ramas:** prohibido hacer `merge` a `main` hasta que el equipo lo autorice. No se hace `push` ni se abre un PR sin que lo pidan.
- **Cumplimiento:** `docs/requisitos.md`, `docs/cumplimiento-normativo.md` y `docs/justificacion-criptografica.md` ya existen. Una tarea que cambie un control, un algoritmo o una clave mantiene alineados esos documentos y la trazabilidad.

## Review Focus

Tres casos que la spec implica, pero que ningún criterio de aceptación nombra explícitamente. Cada uno tiene un test en la tarea dueña:

1. **Usuario con mayúsculas o espacios.** `" ANA "` y `ana` son la misma cuenta en el registro y en el login; registrar `ANA` cuando existe `ana` → 409. → **ATH-2**, `test_usuario_normalizado_en_registro_y_login`.
2. **Rol asignado a mitad de una sesión.** Un permiso asignado (`stego:analyze`) vale en la siguiente request sin volver a entrar, y uno quitado deja de valer igual de rápido. → **ATH-4**, `test_r05_rol_asignado_vale_en_la_siguiente_peticion`.
3. **Imágenes que no son RGB** (RGBA, paleta, escala de grises, 16 bits). `stego` las analiza sin 500. → **STG-2**, `test_modos_de_imagen_no_rgb`.

**Lint local:** `ruff format services/<svc> && ruff check --fix services/<svc>` (ordena imports y quita los que sobran). La CI usa `ruff check` y `ruff format --check`, sin `--fix`.

## Preparación del entorno local (una vez por integrante)

```bash
py -3.13 -m venv .venv
```
(En macOS/Linux: `python3.13 -m venv .venv`.) Actívalo (`.venv\Scripts\Activate.ps1` en PowerShell, `source .venv/bin/activate` en bash) e instala:
```bash
pip install -e "services/shared[dev]"
```
A medida que se creen los servicios, se instalan con `pip install -e services/<svc>`. Para la BD de pruebas:
```bash
docker compose -f deploy/docker-compose.test.yml up -d
```
