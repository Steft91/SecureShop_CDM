# 04 · Gateway (Nginx) — Plan de implementación (rev. 4)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** El gateway es el único punto de entrada al sistema. Termina TLS 1.3, redirige http → https, aplica las cabeceras de seguridad y el rate limit, y enruta cada prefijo a su servicio. En cada request verifica al usuario con `auth_request` a `auth` y propaga su identidad y sus permisos actuales, sin que el cliente pueda falsificarlos (R5, R7, R10, R16). En el primer parcial enruta solo a los dos microservicios: `auth` (cuentas y administración de roles) y `stego`.

**Architecture:**
- Nginx 1.27 con una configuración propia (`nginx.conf` reemplaza la de la imagen).
- Upstreams con variables y el `resolver` de Docker: un servicio redeplegado sigue alcanzable, y uno que todavía no existe responde 503 JSON en vez de impedir el arranque.
- Una sola subpetición interna, `/_auth/user` → `auth GET /internal/verify`. Recibe las cookies y el `Authorization` originales; `auth` responde las cabeceras `X-User-*`.
- Cada `location` incluye **exactamente un** snippet de proxy:
  - `proxy-public.conf` vacía la identidad y el `Authorization`, pero deja pasar las cookies.
  - `proxy-user.conf` hace el `auth_request` y pone la identidad que devolvió `auth`; no deja pasar ni el JWT ni las cookies.
- Todos los snippets inyectan el `X-Service-Token` del gateway desde un Docker secret.

**Tech Stack:** Nginx 1.27-alpine, mkcert, Docker Compose, curl (Git Bash), Postman.

**Spec:** `docs/specs/2026-10-12-chat-seguro-design.md` §4.3–§4.5, §8.1, §9.1 (*Verify*), §13, §15, §20 (riesgo de Postman y la cookie de dispositivo).

## Global Constraints

Las del índice (`2026-10-13-00-indice.md`). En particular:
- Solo TLS 1.3.
- Errores en JSON `{"error": "..."}`.
- Secretos solo desde `/run/secrets`.
- `client_max_body_size` es 16k por defecto y 5m solo en la ruta de análisis.
- Commits en español, sin atribución.

## Review Focus

Ningún caso del índice cae aquí. Hay tres riesgos propios de este archivo:
- **Herencia de `proxy_set_header`.** Una `location` que declara su propio `proxy_set_header` **deja de heredar** los del nivel `server`. Por eso cada `location` incluye un snippet completo y ninguna depende de la herencia. Lo prueban los curl del GW-1 Step 5 (identidad falsificada → 401).
- **Postman sin la cookie `__Host-device`.** Si Postman no la conserva, `verify` responde 401 aunque el Bearer sea válido. Se prueba el primer día (GW-1 Step 7), antes de escribir la colección (PAR-1).
- **Variables compartidas con la subpetición.** El `auth_request` comparte las variables con la petición principal, así que `/_auth/user` usa `$verifier` y nunca `$upstream`. Lo prueba GW-1 Step 6: `/api/stego/analyze` devuelve un veredicto, que solo puede venir de `stego`.
- **`auth` caído.** Si la subpetición falla, Nginx responde 500, que el `error_page` convierte en `503 {"error":"servicio no disponible"}`. Nunca deja pasar la request. Lo prueba GW-1 Step 5 (`docker compose stop auth`).

### Task GW-1: Nginx con TLS 1.3, `auth_request` y las rutas del parcial (R5, R7, R10, R16)

**Files:**
- Create: `gateway/nginx.conf`
- Create: `gateway/snippets/proxy-base.conf`, `gateway/snippets/proxy-public.conf`, `gateway/snippets/proxy-user.conf`, `gateway/snippets/subrequest.conf`
- Create: `gateway/Dockerfile`
- Modify: `deploy/docker-compose.yml` (servicio `gateway`)
- Modify: `docs/trazabilidad-riesgos.md` (filas R7, R10 y R16; verificación manual), `CLAUDE.md` (*Estado actual*)

**Interfaces:**
- Consumes:
  - `GET /internal/verify` de auth (ATH-2), que responde `204` + `X-User-Id`, `X-User-Name`, `X-Session-Id` y `X-User-Perms`, o `401`;
  - las rutas públicas de auth (ATH-2…ATH-4) y stego (STG-3);
  - el secreto `gateway_token_conf` (FND-6; contiene `proxy_set_header X-Service-Token "…";`);
  - las imágenes de la demo en `docs/demo-imagenes/` (STG-4).
- Produces:
  - `https://localhost` con las rutas de la spec §13 que existen en el parcial; cualquier otra ruta responde `404` JSON;
  - hacia los servicios, las cabeceras `X-Service-Token`, `X-Real-IP`, `X-Forwarded-For` (sobrescrita con `$remote_addr`), `X-Forwarded-Proto`, `X-Request-ID` (`$request_id`, sobrescribe el del cliente) y, en las rutas de usuario, `X-User-Id`, `X-User-Name`, `X-Session-Id` y `X-User-Perms`;
  - hacia el cliente, `X-Request-ID` una sola vez, y un registro de acceso JSON por petición.

- [ ] **Step 1: Snippets de proxy**

`gateway/snippets/proxy-base.conf`:
```nginx
# Base de toda petición hacia un servicio. No se incluye sola en una location: va dentro de los demás snippets.
proxy_set_header Host              $host;
proxy_set_header X-Real-IP         $remote_addr;
# Sobrescribe (no concatena): el cliente no puede inyectar una IP falsa.
proxy_set_header X-Forwarded-For   $remote_addr;
proxy_set_header X-Forwarded-Proto https;
# Id de correlación (RNF-19): lo genera nginx y sobrescribe el del cliente. Viaja a los servicios y a auth
# (subpetición). La subpetición comparte variables con la petición, así que es el mismo id.
proxy_set_header X-Request-ID      $request_id;
# proxy_set_header X-Service-Token "<token del gateway>"; (Docker secret, R16)
include /run/secrets/gateway_token_conf;
```

`gateway/snippets/proxy-public.conf`:
```nginx
# Rutas sin sesión (registro y login): se vacía la identidad para que el cliente no la inyecte (R16).
# Las cookies sí pasan: auth las necesita para la cookie de dispositivo.
include /etc/nginx/snippets/proxy-base.conf;
proxy_set_header X-User-Id     "";
proxy_set_header X-User-Name   "";
proxy_set_header X-Session-Id  "";
proxy_set_header X-User-Perms  "";
proxy_set_header Authorization "";
```

`gateway/snippets/proxy-user.conf`:
```nginx
# Rutas de usuario: auth decide (R5). La identidad sale de su respuesta y nunca del cliente.
auth_request     /_auth/user;
auth_request_set $user_id    $upstream_http_x_user_id;
auth_request_set $user_name  $upstream_http_x_user_name;
auth_request_set $session_id $upstream_http_x_session_id;
auth_request_set $user_perms $upstream_http_x_user_perms;
include /etc/nginx/snippets/proxy-base.conf;
proxy_set_header X-User-Id     $user_id;
proxy_set_header X-User-Name   $user_name;
proxy_set_header X-Session-Id  $session_id;
# Vacía si no tiene permisos: Nginx no envía cabeceras vacías y el servicio la lee como "sin permisos".
proxy_set_header X-User-Perms  $user_perms;
# Ni el JWT ni las cookies llegan a los servicios.
proxy_set_header Authorization "";
proxy_set_header Cookie        "";
```

`gateway/snippets/subrequest.conf`:
```nginx
# Subpetición del auth_request: sin cuerpo y con la URI original (sin query) para los eventos de seguridad.
# Solo la base: así llegan a auth el Authorization y las cookies originales.
proxy_pass_request_body off;
proxy_set_header Content-Length "";
proxy_set_header X-Original-URI $uri;
include /etc/nginx/snippets/proxy-base.conf;
```

- [ ] **Step 2: `nginx.conf`**

`gateway/nginx.conf`:
```nginx
# Gateway (spec §13): único punto de entrada a auth y stego.
worker_processes auto;
events { worker_connections 1024; }

http {
    include       /etc/nginx/mime.types;
    default_type  application/octet-stream;
    server_tokens off;
    sendfile      on;

    # DNS interno de Docker: los upstreams se resuelven por request. Un servicio redeplegado (con IP nueva)
    # sigue alcanzable y uno ausente da 503 en vez de impedir el arranque.
    resolver 127.0.0.11 valid=10s ipv6=off;

    # Una línea JSON por petición, con los mismos campos que los servicios (RNF-18). Sin query string
    # ($uri, no $request_uri): nada de la query queda registrado.
    log_format json escape=json '{"ts":"$time_iso8601","service":"gateway","level":"info",'
                                '"request_id":"$request_id","ip":"$remote_addr","method":"$request_method",'
                                '"path":"$uri","status":$status,"bytes":$body_bytes_sent,"request_time_s":$request_time}';
    access_log /dev/stdout json;
    error_log  /dev/stderr warn;

    limit_req_zone  $binary_remote_addr zone=api:10m   rate=10r/s;
    limit_req_zone  $binary_remote_addr zone=login:10m rate=1r/s;
    limit_conn_zone $binary_remote_addr zone=perip:10m;
    limit_req_status  429;
    limit_conn_status 429;

    server {
        listen 80;
        server_name _;
        return 301 https://$host$request_uri;   # http nunca llega a un servicio (R7)
    }

    server {
        listen 443 ssl;
        http2 on;
        server_name _;

        ssl_certificate     /etc/nginx/certs/fullchain.pem;
        ssl_certificate_key /etc/nginx/certs/privkey.pem;
        ssl_protocols       TLSv1.3;
        ssl_session_tickets off;

        client_max_body_size 16k;
        client_body_timeout  10s;
        limit_conn perip 20;

        # Ninguna location declara add_header: si lo hiciera, dejaría de heredar estas.
        add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
        add_header Content-Security-Policy "default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' blob:; connect-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'self'" always;
        add_header X-Content-Type-Options "nosniff" always;
        add_header Referrer-Policy "no-referrer" always;
        add_header Permissions-Policy "camera=(), microphone=(), geolocation=()" always;
        # El usuario cita este id al reportar un error. Los servicios no lo devuelven, así que sale una sola vez.
        add_header X-Request-ID $request_id always;

        error_page 401 = @e401;
        error_page 403 = @e403;
        error_page 404 = @e404;
        error_page 413 = @e413;
        error_page 429 = @e429;
        error_page 500 502 503 504 = @e503;
        location @e401 { default_type application/json; return 401 '{"error":"no autenticado"}'; }
        location @e403 { default_type application/json; return 403 '{"error":"prohibido"}'; }
        location @e404 { default_type application/json; return 404 '{"error":"no encontrado"}'; }
        location @e413 { default_type application/json; return 413 '{"error":"archivo demasiado grande"}'; }
        location @e429 { default_type application/json; return 429 '{"error":"demasiadas solicitudes"}'; }
        location @e503 { default_type application/json; return 503 '{"error":"servicio no disponible"}'; }

        # --- verificación del usuario (subpetición interna) ---
        # La subpetición comparte las variables de la petición principal: si usara $upstream,
        # pisaría el de la ruta y la petición autenticada terminaría en auth. Por eso, $verifier.
        location = /_auth/user {
            internal;
            set $verifier http://auth:8000;
            proxy_pass $verifier/internal/verify;
            include /etc/nginx/snippets/subrequest.conf;
        }

        # --- auth: sin sesión (registro y login) ---
        location ~ ^/api/auth/(register|login)$ {
            limit_req zone=login burst=5 nodelay;
            set $upstream http://auth:8000;
            proxy_pass $upstream;
            include /etc/nginx/snippets/proxy-public.conf;
        }
        location /api/auth/ {
            limit_req zone=api burst=20 nodelay;
            set $upstream http://auth:8000;
            proxy_pass $upstream;
            include /etc/nginx/snippets/proxy-user.conf;
        }

        # --- administración de cuentas y roles (los permisos los exige auth con require_perm) ---
        location /api/admin/ {
            limit_req zone=api burst=20 nodelay;
            set $upstream http://auth:8000;
            proxy_pass $upstream;
            include /etc/nginx/snippets/proxy-user.conf;
        }

        # --- stego ---
        location = /api/stego/analyze {
            client_max_body_size 5m;
            limit_req zone=api burst=20 nodelay;
            set $upstream http://stego:8000;
            proxy_pass $upstream;
            include /etc/nginx/snippets/proxy-user.conf;
        }

        # Nada más existe hacia afuera (R16).
        location /api/      { return 404; }
        location /internal/ { return 404; }
        location /          { return 404; }
    }
}
```

La `location` con regex de `/api/auth/` gana sobre el prefijo `/api/auth/`, porque Nginx evalúa las regex después de recordar el prefijo más largo.

```bash

curl -sI --cacert "$CA" -H "X-Request-ID: del-cliente" https://localhost/api/auth/me | grep -i -c "^x-request-id"

Expected, en orden:
```

exit=35            (cualquier valor distinto de 0: el handshake TLS 1.2 se rechaza)

{"error":"no encontrado"}

- [ ] **Step 7: Postman conserva la cookie de dispositivo (spec §20)**

En Postman: *Settings → Certificates → CA certificates* → `rootCA.pem` (la ruta de `mkcert -CAROOT`). Luego:
1. `POST https://localhost/api/auth/login` con `Origin: https://localhost` y el usuario del Step 6 → copia `access_token`.
2. `GET https://localhost/api/auth/me` con *Authorization → Bearer Token* = ese token.

Expected: `200`. En *Cookies* (debajo de *Send*) aparece `__Host-device` para `localhost`.

Si responde `401`, Postman no conserva la cookie. Anótalo en el ticket de PAR-1: la colección guarda `__Host-device` del login en una variable y la manda en la cabecera `Cookie`.
