# 05 · Servicio `rooms` — Plan de implementación (rev. 4, por tareas)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

> **Por tareas.** Este archivo fija archivos, interfaces, tests y criterios, pero no el código. Antes del incremento 2, el dueño de ROOM-1 escribe el código detallado partiendo de `docs/plans/rev3/2026-10-13-05-rooms.md`. De ahí se reutilizan el empaquetado, Alembic, `Settings`, la normalización de código y alias, el ingreso con cupo atómico, el rate limit y los tests de concurrencia. Se reemplazan las sesiones de sala por la membresía de la cuenta y el CRUD del admin por las acciones del dueño.

**Goal:** Salas tipo Discord. Cualquier usuario con `rooms:create` crea una sala (máximo 2 activas) y queda como dueño. Los demás entran una vez con código + clave + alias y quedan como miembros hasta salir o ser expulsados. El dueño edita, cierra, cede, expulsa con veto y silencia; el admin global (`rooms:manage_any`) puede hacer lo mismo sin leer mensajes ni cambiar la clave. Riesgos R1, R5, R8, R11, R15 y R16.

**Architecture:**
- FastAPI sobre `create_base_app`. Tres routers:
  - `rooms.py`: crear, *Mis salas*, ingresar, salir y ver miembros (`require_user` / `require_perm`).
  - `manage.py`: acciones del dueño y la lista global (`/api/admin/rooms`).
  - `internal.py`: la membresía para `chat` y `media`, y su latido.
- El cupo se toma con `UPDATE … WHERE member_count < max_members` y la membresía se inserta en la **misma transacción**. El `CHECK` y el índice `alias_per_room` son el respaldo.
- El límite de 2 salas y la cesión se serializan por usuario con `pg_advisory_xact_lock(hashtextextended(:user_id, 0))`.
- Los avisos a `chat` (`kick`, `mute`, `close`) son de mejor esfuerzo (`notify.chat`): la decisión ya quedó en la BD y el latido de `chat` la reconcilia.

**Tech Stack:** Python 3.13, FastAPI, SQLAlchemy async, Alembic, argon2-cffi (vía `shared.passwords`), httpx, pytest.

**Spec:** `docs/specs/2026-10-12-chat-seguro-design.md` §7.2, §8.1–§8.2, §9.2–§9.4, §14.2, §14.4, §16.4 (R1, R5, R8, R11, R15, R16).

## Global Constraints

Las del índice (`2026-10-13-00-indice.md`). En particular:
- `text()` con parámetros nombrados; cuerpos con `extra="forbid"`.
- Autorización por permiso (`X-User-Perms`) o por dueño/miembro, siempre leída de la BD de `rooms`; nunca por un campo del cuerpo.
- Errores genéricos: `"sala o clave inválida"`, `"no puedes entrar a esta sala"`, `"sala llena"`, `"alias en uso"`, `"código no disponible"`, `"ya tienes 2 salas activas"`, `"cede la sala antes de salir"`, `"permiso insuficiente"`.
- Argon2id con ≤ 4 cálculos concurrentes; la clave de sala sigue la política de contraseña y es distinta del `code`.
- Commits en español, sin atribución.

## Review Focus

Ningún caso del índice cae aquí. Hay tres riesgos propios de este servicio:
- **El dueño cuenta como miembro.** `member_count` empieza en 1, así que una sala de cupo 5 admite 4 ingresos más. Lo fija `test_r15_ingresos_concurrentes_respetan_el_cupo` (ROOM-2).
- **El alias queda reservado aunque su dueño salga.** Lo hace `alias_per_room`, sin `WHERE`. Quien vuelve a entrar después de salir recupera su fila (`ON CONFLICT (room_id, user_id)`), pero otro usuario no puede tomar ese alias: `test_alias_de_quien_salio_sigue_reservado` (ROOM-2).
- **El admin global no es miembro.** Administra la sala, pero `/internal/membership` le responde 404, así que no lee mensajes ni sube archivos: `test_admin_global_no_es_miembro` (ROOM-4).
